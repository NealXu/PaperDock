# PDF 三个 VIP 功能的独立实现与可行性方案

日期：2026-10-22

目标：分析 WPS PDF 拆分中“扫描型 PDF / 可搜索 PDF / 水印”三个 VIP 功能的实现，并独立做出功能等价的本地工具。

边界：只参考公开可见的行为和本地程序的实现结构，不复用 WPS 代码、字体、OCR 模型或私有接口。下面的工具是独立实现。

> 归档说明（2026-10-24）：当前实际交付版是 `app/` 中的 C# WPF 应用。早期 Python MVP 仅作为研究与行为对照记录；其代码和打包产物已从交付目录清理，不再作为运行依赖。

## 一、可行性结论

| 功能 | 可行性 | 判断 |
| --- | --- | --- |
| 扫描型 PDF | 高 | 本质是把每页渲染成图片再封装成 PDF，技术成熟、结果稳定 |
| 水印 | 高 | 本质是叠加半透明文字或图片，位置、角度、透明度都可控 |
| 可搜索 PDF | 中高 | 图片 + OCR + 不可见文字层即可；效果取决于扫描质量和 OCR 引擎 |

本机已经具备实现条件：Python 3.12、PyMuPDF 1.28.2、Windows 自带离线 OCR（zh-Hans-CN）。不需要安装 Tesseract、PaddleOCR 或任何在线服务。

## 二、WPS 的实现拆解

### 1. 扫描型 PDF

在 `kp2wapp.dll` 中可以看到 `pdf_2img_pdf`、`pdf_2img_pdf_local`、`ATT_VIP_MUST_P2ImgPdf` 等标识。它的核心不是“扫描”，而是：

1. 按目标分辨率把源页面渲染成位图；
2. 用 JPEG/PNG 压缩；
3. 新建同尺寸页面，把整页图片放进去；
4. 不写入文字层。

因此输出页看起来像扫描件，但文字、链接、书签都会丢失，文件大小取决于分辨率和压缩质量。

### 2. 可搜索 PDF

对应 `PdfOcr`、`Converter_SearchablePDF`、`OutputType_SearchablePDF`、`solidtoocr`、`pc_pdf_ocr_v2` 等标识。典型流程是：

1. 页面渲染成图片；
2. OCR 识别文字和坐标；
3. 在图片上方写入**不可见文字**（PDF 文本渲染模式 3）；
4. 每个词/行按 OCR 坐标定位，保证可以选中和搜索。

难点不在“写文字”，而在坐标缩放、中文断行、字体 ToUnicode 和 OCR 误差。WPS 同时存在本地 OCR 与在线 OCR 的痕迹，本次实现只走本地离线路径。

### 3. 水印

对应 `imagepdf_watermark`、`addTrialWatermark`、`KPdfWaterMarkDlg` 等标识。实现方式是把水印作为页面内容流的一部分叠加：

- 文字水印：字体、字号、颜色、透明度、旋转角度、平铺间距；
- 图片水印：透明度、居中、缩放；
- 非会员路径会出现试用水印，会员路径允许自定义或去除。

## 三、技术选型

下表是已经完成端到端验证的 **Python MVP** 选型。小体积桌面交付版另行采用 C# + .NET Framework 4.8 + WPF，具体约束见 P6 和第九节；两套实现不混用运行时。

| 层 | 选择 | 原因 |
| --- | --- | --- |
| PDF 读写/渲染 | PyMuPDF 1.28.2 | 已在本机安装；渲染、插图片、不可见文字、叠加层、拆分都很直接 |
| OCR | Windows.Media.Ocr（zh-Hans-CN） | 离线、无需安装；本机已有简体中文识别包 |
| CLI | Python `argparse` | 标准库，零额外依赖 |
| 图片压缩 | PyMuPDF 内置 JPEG 编码 | 不额外引入 Pillow 依赖 |

没有选 Tesseract/PaddleOCR：本机未安装；Windows OCR 对本次的清晰扫描页已经够用。若后续需要更高精度或更多语言，再把 OCR 做成适配器。

## 四、工具结构

```
pdfvip.py
  ├─ split planner      固定页数 / 自定义范围 / 等分
  ├─ merge planner      多文件顺序 / 每份页范围（P1）
  ├─ renderer           页面 → JPEG（DPI、质量可调）
  ├─ OCR                PowerShell 5.1 → Windows OCR → JSON（行/词/坐标）
  ├─ text layer         坐标缩放 → render_mode=3 不可见文字
  ├─ watermark          文字平铺 / 图片居中，透明度与角度可调
  └─ writer             每份输出独立 PDF，保留页数和顺序
ocr_windows.ps1         批量识别目录内 JPG，输出 UTF-8 JSON
```

数据流：

```
源 PDF
  → 选择页 → 渲染 JPEG
  → [可搜索] OCR → 坐标换算 → 不可见文字层
  → [水印] 叠加文字/图片
  → 输出 PDF
```

合并的数据流：

```
多个 PDF + 各自页范围
  → 按列表顺序逐份 insert_pdf
  → [水印] 叠加文字/图片
  → 输出一个 PDF
```

### 基本拆分（已实现）

WPS 截图里的拆分能力包括：固定页数、自定义范围、按文档数量均分；右侧实时显示“将拆分为 N 份”，并支持输出类型、文档加密、水印和输出位置。当前账号下 WPS 对基本拆分也弹出了权益提示，说明它把拆分本身也纳入了权益控制。

本工具的拆分是基础能力，不设 VIP：

| WPS 界面能力 | 本工具 |
| --- | --- |
| 按固定页数拆分 | `--split fixed --per N` |
| 按自定义范围拆分 | `--split ranges --ranges 1-3,5` |
| 按文档数量均分 | `--split count --parts N` |
| 页码范围与份数提示 | 输出文件名带 `p起始-结束`，可直接核对 |
| 扫描型/可搜索输出 | `--output image` / `--output searchable` |
| 水印 | `--watermark` / `--watermark-image` |
| 文档加密 | 未实现，见限制 |

验收标准：每份页数等于所选范围；页序不变；不丢页、不重复；页面尺寸与旋转保持原样。

### 基本合并（P1）

WPS 截图里的合并能力包括：多文件列表、全选、排序、清空、添加文件、每份文件单独选页范围、预览、输出名称、输出类型、文档加密、水印和输出位置，底部实时汇总“将合并 N 份文档，共 M 页”。当前账号下同样被权益提示拦截。

P1 先做最小可用版本：

```text
pdfvip.py merge a.pdf b.pdf -o merged.pdf
```

规则：按命令行输入顺序合并全部页；不做重压缩，尽量保留原页面内容；可选文字/图片水印。

P1.1 增加每份文件独立页范围，用 JSON 清单避免 Windows 路径里的冒号歧义：

```json
{
  "items": [
    {"path": "a.pdf", "pages": "1-11"},
    {"path": "b.pdf", "pages": "2-4"}
  ]
}
```

```text
pdfvip.py merge --manifest merge.json -o merged.pdf
```

验收标准：输出页数等于所有 `pages` 选择结果之和；页序与清单一致；页面尺寸/旋转保持；失败时明确报出是哪个文件、哪个范围，不产出半成品。

## 六、分阶段实施方案

### P0：核心 MVP（已完成）

- 拆分：固定页数、自定义范围、等分；
- 扫描型 PDF；
- 可搜索 PDF（Windows 本地 OCR）；
- 文字/图片水印；
- 自动化验证脚本。

### P1：基本合并（已完成 MVP）

- PDF 合并（先全文件顺序合并，再支持每份文件独立页范围的 JSON 清单）；

验收结果：合并后的页数等于所有选中页之和，顺序、页面尺寸与源文件一致；拆分输出不丢页/不重复。多文件批量、输出清单与进度条移到后续优化，不影响 10 项功能的验收。

### P2：Office 交付（已完成 MVP）

- PDF → PPT：每页作为整页图片放入幻灯片，优先保证“看起来一样”；
- PDF → Word：文本块 + 图片写入 DOCX，优先保证“可编辑”；
- Word 的扫描页可加 `--ocr`；PPT 始终是整页图片，不做文字重建。

验收结果：PPT 页数与 PDF 一致；Word 能检出关键标题/段落；扫描 PDF 加 `--ocr` 后不出现空白文档。

### P3：表格与版式（已完成 MVP）

- PDF → Excel：`pdfplumber` 的表格识别 + 单元格合并规则；
- Word 基础版式：文本块顺序、字号、图片；
- 复杂分栏、浮动元素和低置信度标记留到后续优化。

验收结果：规则表格的行列数与样例一致；复杂版式在限制章节中明确标注为不保证。

### P4：CAD 与 CAJ（已完成 MVP）

- PDF → CAD：矢量线框输出 DXF；扫描图写栅格底图，不伪装成矢量；
- CAD → PDF：DXF 直接渲染；DWG 走 LibreDWG `dwg2dxf` 或 ODA；
- CAJ → PDF：内置 `caj2pdf`，支持部分 CAJ/HN；失败时明确报错。

验收：只对声明支持的输入格式验收；不支持的格式明确报错，不静默产出错误文件。

### P5：桌面 GUI（Python MVP 与 WPF 版均已完成）

当前高保真界面稿在 `design/v5-fluent/`，只保留拆分、合并、Word/Excel/PPT 转换和 OCR 设置，不显示 CAD/DWG/CAJ。v5 选定 Windows 原生方向，采用左侧导航、渐进披露和单一主操作，复杂选项收进“更多选项”。小体积版本推荐用 .NET Framework 4.8 + WPF 重做。

### 1. 产品边界

小体积 WPF 版本的交付范围固定为：

- PDF 拆分：固定页数、自定义范围、按数量均分；
- PDF 合并：文件顺序、每份文件可选页范围；
- 扫描型 PDF；
- 水印；
- 可搜索 PDF；
- PDF → Word / Excel / PPT；
- 系统 OCR 与离线 OCR 包导入。

PDF → CAD、CAD → PDF、DWG → PDF、CAJ → PDF、加密、权限控制、批量队列和书签保留不进入本次 WPF 交付，也不在界面中出现入口。现有 Python 工具里的这些实现保留为历史能力，不混入小体积版本。

### 2. 转换质量口径

- Word：保留文字、图片和基本段落；复杂分栏、浮动对象、公式和精确排版不保证。
- Excel：只对规则表格可靠；合并单元格、无框表和扫描表格不承诺结构还原。
- PPT：每页作为整页图片输出，视觉一致，但文字不可编辑。
- 拆分和合并属于核心高可信能力，必须保证不丢页、不重复、页序正确。

如果要求 Office 转换达到 WPS 版面级还原，需要重新评估 10 MB 目标和第三方引擎授权。

### 3. 文件安全

- 原文件只读，不修改原文件。
- 输出先写临时文件，成功后再原子改名。
- 不覆盖已有文件；重名时自动追加序号。
- 失败、取消或磁盘不足时清理临时文件，不留下半成品。
- 加密 PDF、损坏 PDF、零页 PDF 和范围越界必须给出具体错误，不静默跳过。
- 长路径、中文路径、空格路径均纳入验收。

### 4. OCR 包

离线 OCR 包按不可信输入处理：

- 包内必须有版本、语言、适用平台、文件清单和 SHA-256 校验值。
- 导入前校验格式和路径，拒绝路径穿越、脚本和未知可执行文件。
- 只安装模型与必要运行组件，不要求管理员权限。
- 支持删除、切换默认引擎和失败回滚。
- 不自动联网下载或更新 OCR 包。
- OCR 包及其语言模型的再分发许可需要单独审核。

### 5. 组件与许可

- 固定 `PDFsharp-wpf 6.2.4`（MIT）与 `PdfPig 0.1.16`（Apache-2.0）。
- **不得自动升级到 PDFsharp 6.5 或 7 预览**；这些版本当前标为 AGPL-3.0-only。
- `DocumentFormat.OpenXml 3.5.1` 单个主要程序集约 7.99 MB，默认不引入；Office 文件优先用 `System.IO.Compression` 和最小 Open XML 结构生成。
- 需要保留程序集绑定重定向，特别是日志抽象和 `System.Runtime.CompilerServices.Unsafe`。
- 不复制 WPS 的代码、资源、图标、提示文案或字体；独立实现，不使用 WPS 商标，不绕过其 VIP 校验。
- 不随安装包分发 Segoe UI、微软雅黑等系统字体。
- 对外分发前由法务确认逆向研究和第三方组件许可边界。

### 6. 安装与分发

- 面向个人用户按用户安装，不要求管理员权限。
- 启动时检测 .NET Framework 4.8，缺失时给出明确说明。
- 基础安装包目标为 10 MB 以内，OCR 包单独导入。
- 安装、升级、卸载不删除用户 OCR 包和输出设置。
- 正式发布前使用代码签名证书签名；未签名包必须明确提示 SmartScreen/应用控制策略风险。
- 不接管 PDF 文件关联，不默认常驻，不做联网遥测。

### 7. 界面与可访问性

- v5 Fluent 定稿必须适配 1366×768 和 125%/150% 缩放。
- 所有操作支持键盘；合并排序除拖动外提供上移/下移按钮。

## 十、限制与风险

1. PDF→Word 采用文本块 + 图片的简单版式；复杂分栏、浮动图片、精确排版不保证。
2. PDF→Excel 只对规则表格可靠；合并单元格、无框表、扫描表格不做结构重建。
3. PDF→PPT 是整页图片版，视觉一致但文字不可编辑。
4. PDF→CAD 的矢量提取是尽力而为；扫描页写栅格底图，不做图像矢量化。
5. DWG→PDF 需要 LibreDWG `dwg2dxf` 或 ODA File Converter，二进制不随项目分发。
6. CAJ 使用上游 `caj2pdf`，只支持部分 CAJ/HN；本机 HN 样本转换失败，CAJ 样本成功。
7. 可搜索模式会栅格化页面，原 PDF 的矢量文字、链接、书签不会保留。
8. OCR 只装了简体中文识别包；英文可识别但精度不如专用英文模型，其他语言需额外语言包。
9. 未实现 PDF 加密、权限控制、PDF/A、多文件批量；WPF 版已实现但安装包尚未代码签名。
10. 水印是页面内容，不是安全边界；有编辑能力的用户仍可移除。
11. 图片水印当前为居中叠加，`--watermark-angle` 只作用于文字水印。
12. 扫描型文件通常比原 PDF 大，需在 DPI、JPEG 质量和体积之间取舍。
13. PDF→PPT 以第一页尺寸建幻灯片；混合页面尺寸会按统一画布缩放。
14. PDF 合并当前不保留书签/大纲，只保证页序和页面内容。
15. DXF→PDF 当前渲染 LINE、LWPOLYLINE、CIRCLE、ARC、TEXT、MTEXT；其他实体会跳过。

## 十一、后续优化

1. 多文件批量、输出清单 JSON、进度条与失败重试；
2. 低置信度表格/段落标记，避免“看起来成功但数据错了”；
3. OCR 适配器：Windows OCR / Tesseract / PaddleOCR 可切换；
4. 按词级坐标写入，提升选择精度；
5. 加密 PDF 输入输出与权限设置；
6. 复杂 Office/CAD 转换可选接本地 LibreOffice 或服务端引擎，提升版式保真；
7. WPF 交付版采用 C# 重新实现 PDF/Office 核心，不复用 PySide6 外壳。

## 十二、REA 与方案更新的关系

不需要“每新增一个功能就先把 WPS 逆一遍”。REA 适合回答“WPS 是怎么做的、走本地还是在线、门禁在哪”，而格式转换的质量问题更适合用**受控样本 + 输出对比**回答。

| 功能组 | 是否必须先做 REA | 原因 |
| --- | --- | --- |
| 拆分、合并、扫描型、水印 | 不需要 | 都是标准 PDF 操作，PyMuPDF 可直接实现 |
| PDF 转 Word/Excel/PPT | 建议做一次定向 REA + 行为样本 | 需要确认本地/在线切换条件、输出结构和可接受的版式保真 |
| PDF 转 CAD、CAD 转 PDF | 建议做定向 REA + 外部引擎评估 | 需要区分矢量/扫描输入，确认 WPS 是否走在线转换 |
| CAJ 转 PDF | 建议做定向 REA + 授权工具评估 | CAJ 为专有格式，需确认本地转换器是否存在及可用性 |

现有 REA 证据已经给出总体结论：WPS 采用**本地转换 + 在线兜底**。`kp2wapp.dll` 里同时存在 `pdf_2doc_local`、`pdf_2et_local`、`pdf_2ppt_local`、`pdf_merge_local`、`pdf_caj2pdf_local`，以及 `ATT_UseOnlineConverter_Normal/Scanner/Garbled_P2*`、`Pdf2OfficeOnlineConverter`、`Pdf2CadOnlineConverter`。

建议顺序：

1. 先按当前方案做 P1（合并/批量），不依赖 REA；
2. 进入 P2/P3 前，用 3 类样本（正常数字版、扫描版、乱码/复杂版式）生成 WPS 参考输出，记录页数、文字、表格、图片和版式；
3. 只对差异点做定向 REA（例如为何切在线、CAJ 本地转换器如何调用），不扩大到整包逆向；
4. 用对比结果更新方案中的“保真等级”和验收标准，再决定是否引入服务端/外部引擎。
